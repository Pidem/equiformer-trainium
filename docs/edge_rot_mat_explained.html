The Per-Edge Rotation Matrix

A visual walkthrough of init_edge_rot_mat in EquiformerV3 — what it computes, why it exists, and why it forces tensors back to the CPU on Neuron.

File: equiformer_v3/src/fairchem/experimental/models/equiformer_v3/edge_rot_mat.py:11
Caller: EquiformerV3._forward_edge — runs once per forward pass, on every edge in the graph.

1. What is an "edge" and why does it need a rotation?

EquiformerV3 is a graph neural network for atomic systems. Atoms are nodes; an "edge" connects two atoms within some cutoff radius. For your NaCl run there were 24 atoms and 460 edges.

The model is equivariant: rotating the input molecule should rotate the predicted forces in the same way. To enforce that, it expresses every interaction along an edge in a local frame aligned with the edge direction — and then transforms features back with Wigner-D matrices. init_edge_rot_mat builds that local frame for every edge.

Figure 1. One rotation matrix per edge converts global xyz coordinates into the edge's local frame.

2. The construction — Gram–Schmidt with a random tiebreaker

For each edge we need three orthogonal unit vectors x̂, ŷ, ẑ. The first one is easy — it's the edge itself. The other two are built so that x̂ aligns with the model's canonical y-axis after rotation.

Figure 2. The three-step construction. The two highlighted ops are not implemented in the Neuron backend.

The actual code, annotated

norm_x      = edge_vec_0 / ‖edge_vec_0‖                       Neuron

edge_vec_2  = torch.rand_like(edge_vec_0) - 0.5               CPU fallback (uniform_)
edge_vec_2 /= ‖edge_vec_2‖

# tiebreaker: try 90°-rotated copies if random vec ≈ parallel to x̂
edge_vec_2b, edge_vec_2c = ...rotated copies...               Neuron
edge_vec_2  = where(|x̂·v| largest, swap)                     Neuron

norm_z = torch.cross(norm_x, edge_vec_2, dim=1)               CPU fallback (linalg_cross)
norm_z = norm_z / ‖norm_z‖
norm_y = torch.cross(norm_x, norm_z, dim=1)                   CPU fallback (linalg_cross)

edge_rot_mat = stack([ẑ, x̂, ŷ]).transpose(1, 2)              Neuron

4. Why it lands on the CPU

Two ops in this routine are not implemented in the Neuron backend:

aten::linalg_cross

torch.cross(a, b, dim=1) — invoked twice, once for ẑ and once for ŷ. The Neuron runtime intercepts the call, copies a and b back to host memory, runs the cross product on CPU, and copies the result back to the device.

aten::uniform_

torch.rand_like(...) — used to pick a "random" auxiliary vector to ensure non-collinearity with x̂. The on-device RNG isn't wired up, so this also bounces through the host.

Figure 3. Each fallback op forces a device→host→device round-trip. The transfer cost dwarfs the op itself.

From the profiler: aten::_to_copy alone accounted for ~502 ms of CPU time across 1,235 invocations in one forward pass. The cross product itself is three multiplies and three subtractions — trivial on-device — but the host round-trip dominates.

Pure-PyTorch replacement (already executes on Neuron)

def cross_dim1(a, b):
    return torch.stack([
        a[:, 1] * b[:, 2] - a[:, 2] * b[:, 1],
        a[:, 2] * b[:, 0] - a[:, 0] * b[:, 2],
        a[:, 0] * b[:, 1] - a[:, 1] * b[:, 0],
    ], dim=1)

And the random tiebreaker can be replaced with a deterministic non-axis-aligned constant ([1, 1, 1] / √3), since its only requirement is "not parallel to x̂".

Bottom line. init_edge_rot_mat is a small, well-defined geometry routine that builds a per-edge orthonormal frame. It looks innocent in PyTorch — three lines of cross-product and normalize — but two of its calls trigger CPU fallback, and because it runs over every edge each forward pass, the resulting host↔device traffic is the single largest CPU-time line item in the profile. Rewriting cross as explicit indexing and replacing the RNG with a constant would eliminate the round-trips entirely.
