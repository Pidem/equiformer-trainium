Spherical Harmonics — From Direction to Coefficients

A concrete walkthrough of what Y_l^m(θ, φ) actually computes, with real numbers for real directions.

The one-line summary: Spherical harmonics take a direction (a point on the unit sphere) and produce a fixed-size vector of numbers that encodes "which direction" in a rotation-friendly way.

1. The input: a direction on the sphere

Start with an edge vector between two atoms:

r_ij = pos[j] - pos[i] = [1.5, 0.8, 2.1]   # displacement in Å

Separate into distance and direction:

distance  = ‖r_ij‖ = 2.77 Å                  # how far (→ radial basis)
direction = r_ij / ‖r_ij‖ = [0.54, 0.29, 0.76] # which way (→ spherical harmonics)

The direction is a unit vector — a point on the sphere. We can also write it in spherical coordinates:

θ = arccos(z) = arccos(0.76) = 40.5°    # polar angle from z-axis
φ = arctan2(y, x) = arctan2(0.29, 0.54) = 28.3°   # azimuthal angle in xy-plane

Figure 1. A direction on the unit sphere is the input to spherical harmonics.

2. The output: coefficients at each level

For our example direction [0.54, 0.29, 0.76], here are the actual real spherical harmonic values:

Level lComponents (2l+1)Formula (real SH)Values for our direction
l=0 1 Y_0^0 = 1 (constant) [1.00]
l=1 3 Y_1^{-1} = y, Y_1^0 = z, Y_1^1 = x [0.29, 0.76, 0.54]
l=2 5 xy, yz, 3z²−1, xz, x²−y² (scaled) [0.31, 0.44, 0.38, 0.82, 0.21]
l=3 7 cubic polynomials in x,y,z [..7 numbers..]
Key observation: l=1 is literally just the xyz components of the unit vector! Higher l values are polynomial combinations of x, y, z that capture finer angular patterns.

For lmax=6, one direction produces (6+1)² = 49 numbers.

4. Concrete example: three different directions

Let's see how the SH coefficients differ for three edge directions:

DirectionUnit vectorl=0l=1 [y, z, x]Interpretation
Along +z (up) [0, 0, 1] 1 [0, 1, 0] All "z-ness", no x or y
Along +x (right) [1, 0, 0] 1 [0, 0, 1] All "x-ness"
45° in xz-plane [0.71, 0, 0.71] 1 [0, 0.71, 0.71] Equal x and z

Notice: l=0 is always 1 (it doesn't encode direction). The direction information starts at l=1. At l=1, it's literally the Cartesian components. At l=2+, you get products that distinguish "pointing along x" from "pointing at 45° between x and z" even more precisely.

5. The formulas (real spherical harmonics)

In equivariant GNNs we use real spherical harmonics (no complex numbers). They're just polynomials in x, y, z of the unit vector:

l=0:  Y_0^0  = 1

l=1:  Y_1^-1 = y
      Y_1^0  = z
      Y_1^1  = x

l=2:  Y_2^-2 = √3 · xy
      Y_2^-1 = √3 · yz
      Y_2^0  = ½(3z² − 1)
      Y_2^1  = √3 · xz
      Y_2^2  = ½√3 · (x² − y²)

l=3:  Y_3^-3 = ½√(5/2) · y(3x² − y²)
      Y_3^-2 = √15 · xyz
      Y_3^-1 = ½√(3/2) · y(5z² − 1)
      Y_3^0  = ½(5z³ − 3z)
      Y_3^1  = ½√(3/2) · x(5z² − 1)
      Y_3^2  = ½√15 · z(x² − y²)
      Y_3^3  = ½√(5/2) · x(x² − 3y²)

(Normalization conventions vary — e3nn uses a specific one. The pattern is: degree-l polynomials in x,y,z restricted to the unit sphere.)

Why polynomials? Because polynomials of degree l in (x,y,z) restricted to the sphere form exactly the space of functions that transforms via a (2l+1)×(2l+1) Wigner-D matrix under rotation. This is a theorem from representation theory — it's not a design choice, it's the unique answer.

6. One vector? SH add nothing. The value comes from operations.

This is a common point of confusion: if you have a single direction, converting it to spherical harmonics is just a lossless re-encoding. You get the same information back in a different format. No new information appears.

Key insight: Spherical harmonics are not chosen because they're a better way to store a direction. They're chosen because they make operations on directions equivariant by construction.

Figure 3. SH are a representation chosen for the operations you'll perform, not for storage efficiency.

Analogy: Complex numbers don't help you store a single 2D point better than (x, y). But they make rotations trivial (multiply by e^{iθ}) and composition clean (multiply two complex numbers). You choose the representation for what you'll do with it, not how you'll store it. Spherical harmonics are the same idea in 3D for angular information.

7. Why not just use the xyz vector directly?

Just xyz (l=1 only)
  • 3 numbers per direction
  • Can only represent dipole patterns
  • Can't distinguish "neighbor along x" from "two neighbors symmetric about x" after aggregation
  • Information lost when you sum over neighbors
Full SH up to lmax
  • (lmax+1)² numbers per direction
  • Captures arbitrarily fine angular patterns
  • After summing over neighbors, higher-l components survive and encode the angular distribution
  • Each l-block rotates independently → equivariance is trivial

The aggregation problem

When atom i collects messages from all its neighbors, it sums them. If you only have l=1 (vectors), two neighbors at opposite directions cancel out — you lose information. With l=2, you can tell "I have neighbors along the x-axis" (whether +x or −x) because x² is positive either way.

Figure 3. Higher-l components survive aggregation where vectors cancel.

8. The rotation guarantee

The magic property: if you rotate the input direction by rotation R, the SH coefficients at level l transform by the Wigner-D matrix D^l(R):

Y_l^m(R · r̂)  =  Σ_m'  D^l_{mm'}(R) · Y_l^m'(r̂)

In matrix form for each l:

LevelSize of D^lWhat it means
l=01×1 (= 1)Scalar — doesn't change under rotation
l=13×3Same as the 3D rotation matrix R itself
l=25×5Derived from R, mixes the 5 components among themselves
l=37×7Derived from R, mixes the 7 components among themselves
This is the entire reason EquiformerV3 works.

Because each l-block transforms independently and predictably, the model can:
  1. Store features as SH coefficients at each l
  2. Process them through attention and FFN layers
  3. Know exactly how to rotate them when needed (multiply by D^l)
  4. Read off the l=0 part as energy (invariant) and l=1 part as forces (vector)
Equivariance is guaranteed by linear algebra, not learned from data.

9. Putting it all together: one edge in EquiformerV3

# Given: edge from atom i to atom j
r_ij = pos[j] - pos[i]                    # [3] displacement
dist = torch.norm(r_ij)                    # scalar distance
r_hat = r_ij / dist                        # [3] unit direction

# Spherical harmonics of the direction (computed via edge_rot_mat + Wigner-D)
Y = spherical_harmonics(r_hat, lmax=6)     # [49] coefficients
# Y[0]     = l=0 (1 number)  — always 1
# Y[1:4]   = l=1 (3 numbers) — the xyz direction
# Y[4:9]   = l=2 (5 numbers) — quadratic angular patterns
# Y[9:16]  = l=3 (7 numbers) — cubic patterns
# ...
# Y[36:49] = l=6 (13 numbers) — highest angular detail

# Radial basis (distance encoding)
W = radial_basis(dist)                     # [num_radial_basis] — "how far"

# Message: combine sender features with angular filter, weighted by distance
message = tensor_product(features_j, Y) * W   # equivariant combination
Summary:
  • Input: a direction (unit vector on the sphere)
  • Output: (lmax+1)² numbers — the "fingerprint" of that direction in a rotation-friendly basis
  • l=0: "a neighbor exists" (no direction info)
  • l=1: "it's in this direction" (the vector itself)
  • l=2+: "here's the fine angular structure" (survives aggregation, enables richer representations)
  • Rotation: each l-block transforms independently via a known (2l+1)×(2l+1) matrix
