What the model takes as input

Equiformer is a graph neural network for atomic systems. The input is a single batched "data" object containing the atoms and the bonds within a cutoff radius.

Background: spherical harmonics, in one minute

EquiformerV3 represents per-edge directions and per-node features as spherical-harmonic coefficients. Why? Because rotation acts cleanly on this representation: each "level" l transforms independently via a (2l+1)×(2l+1) matrix (the Wigner-D matrix). That's what lets the model be exactly rotation-equivariant, and it's why several of the kernels we wrote target the Wigner-D path.

The full walkthrough lives in spherical_harmonics_explained.html. The condensed version below covers what's needed to read the rest of this document.

A direction is a single point on the sphere; spherical harmonics turn it into (lmax+1)² coefficients structured by level l. Each level transforms independently under rotation.

Why levels matter — the cancellation argument

If you only kept l=1 (the xyz vector), you'd lose information whenever an atom has neighbors in opposite directions: [-1,0,0] + [+1,0,0] = [0,0,0]. Higher levels survive that cancellation because they're polynomials — x² is positive whether x is +1 or −1.

Higher-l components encode angular patterns that survive aggregation. This is exactly why the Wigner-D chain is in the hot path — every edge produces one.

Connecting back to the patches. Two of our five patches target the Wigner-D code path: wigner_cache (caches the per-l index tensors used to build each Xθ) and wigner_nki_kernel (fuses the entire Xα·J·Xβ·J·Xγ chain into one NKI call). The third — edge_rot_mat_nki — produces the per-edge frame from which the Euler angles α, β, γ are extracted, so it feeds directly into the Wigner-D computation.

Why stages ① and ② dominate optimization work

Stage ④ is where the FLOPs are — but it's essentially a pile of linear + softmax + layer_norm, all of which lower well to Neuron's matmul and activation engines. Stages ① and ② are different: they're geometry, not deep learning. They run small ops on small tensors ([1,3,3] cell vectors; [E,3] edge vectors; [E,3,3] rotation matrices), and many of those ops (cross, atan2, acos, rand_like) aren't yet implemented in the Neuron backend.

Per fallback, the cost isn't the math — it's the host round-trip. With ~6 fallback ops × ~60 invocations across the 460-edge graph, the dispatcher overhead becomes dominant. This is exactly where the ablation patches focus.

Why these specific ops fall back to CPU

"Falls back to CPU" doesn't mean the op is hard. It means the op isn't implemented in the Neuron backend yet — and the reasons differ from op to op. They split into three categories, each with a different fix path.

Three categories of CPU fallback. Each one calls for a different fix.

What about sort.values_stable?

Sort actually has two reasons it's hard:

Sort lives in category C (the output shape is fine, but it's gather-heavy and serial) plus a SIMD-mismatch problem on top. It's the hardest of the bunch and the one we didn't attack — for our PBC graph build, the cost is acceptable because it runs on [1, 3] tensors.

Reading the categories. Patches 4, 5, and our wigner kernel all attack category A — the easy ones. Patch 4 also handles category B (replaces rand_like with a constant). Category C — masked_select, repeat_interleave, sort — are the structurally hard ones that require either dynamic-shape compiler support or a model rewrite to remove. That's why our final 6 remaining fallbacks are dominated by category C.

The hidden cost of .item() — one Python line, three problems

EquiformerV3's PBC graph construction has three innocent-looking .item() calls inside radius_graph_pbc (in core/common/utils.py):

if not torch.any(data.pbc[:, i]).item():                        # line 633
    rep_a1 = data.cell.new_zeros(1)
elif torch.all(data.pbc[:, i]).item():                      # line 635
    rep_a1 = torch.ceil(radius * inv_min_dist_a1)

unit_cell = torch.cartesian_prod(*[
    torch.arange(-rep.item(), rep.item()+1, ...)        # line 720
    for rep in max_rep
])

.item() looks like a value extraction. In reality it's three things at once: a host-sync barrier, a graph break, and (when the value drives a shape) a recompilation trigger.

Problem 1: forced device-host synchronization

.item() requires the value, which means the device must finish computing it before Python can continue. The async pipeline collapses into a serial round-trip.

Problem 2: graph break — one fused graph becomes two

The compiler can't fuse ops on either side of .item() — it needs the intermediate scalar to make a Python decision, which means whatever was one graph is now two. Two compilations, two NEFFs, two launches.

Problem 3: shape-dependent recompilation cascade

When the .item() value drives a downstream tensor's shape, every distinct value becomes a new compilation. The Neuron compiler caches by graph signature, and the signature includes shapes.

What this looked like in our run

347 NEFFs in eager mode

When we tried to capture an end-to-end profile in eager mode (NEURON_RT_INSPECT_ENABLE=1), the runtime dumped 347 separate NEFF files for a single forward pass. Many of those came from this exact pattern: every .item() in radius_graph_pbc, every distinct PBC repeat count, every distinct PBC branch became a fresh compilation. Aggregating profile data across 347 NEFFs into a single timeline isn't supported by neuron-explorer today.

torch.compile blocked

The dynamo backend can't trace EquiformerV3 end-to-end. .item() is one of the hard blockers — when dynamo sees a tensor value flow into Python control flow, it stops the trace and falls back to eager. Two of our four .item() calls drive if/elif branches, which forces a graph break during tracing on top of the runtime cost.

The recommended fix. Move radius_graph_pbc outside the traced region — run graph construction on the host once, feed pre-built edge_index, cell_offsets, and edge_distance_vec into a fixed-shape forward. That removes all four .item() calls from the device path in one move, lets the rest of the model trace as a single graph, and is the same pattern we'd recommend to any customer porting a PyG-style model.

Scatter / gather — the heart of GNN message passing

The edge_index tensor is a pointer-style index. Every layer of a graph neural network turns it into two operations: gather (look up source/target features for each edge) and scatter (aggregate edge messages back to nodes). This is the inner loop of every PyG model, including Equiformer.

A single GNN layer = gather source/target features → compute messages → scatter into nodes. edge_index is the indirection table that drives both directions.

Why scatter/gather is hard on accelerators

Random memory access

Matmul hardware loves contiguous, predictable memory. Scatter writes go to arbitrary addresses determined at runtime by edge_index. The compiler can't prefetch, can't align to partition boundaries, can't fuse cleanly with surrounding ops.

Atomic accumulation

The collisions in the diagram (multiple messages → same target node) require atomic adds in hardware. Trainium supports this for scatter_add_ / index_add_ via nisa.dma_compute(reduce_op=add), but the implementation has constraints (unique-index hint required for some variants).

Output shape sometimes data-dependent

scatter_reduce.two_out returns both reduced values and argmax indices. The argmax tensor has shape [N] but its contents depend on input values — a category C problem from the previous section. This variant falls back on Neuron today.

What does work well

aten::index_select (the gather side) and aten::index_add_ (scatter-add by index) both ran on Neuron in our profile. The basic message-passing primitive is supported — it's the variants and reductions that have gaps.

Where each patch sits in the forward pass

What each patch does

1. PYTHON wigner_cache — +0.11× speedup

Target: wigner._z_rot_mat(angle, l), called 6× per forward (3 angles × 2 layers).

What it patches: The function builds a sparse rotation matrix where cosines lie on the diagonal and sines on the antidiagonal. Each call rebuilt the index tensors from scratch:

inds          = torch.arange(0, 2*l+1, ...)      # [0, 1, 2, ..., 2l]
reversed_inds = torch.arange(2*l, -1, -1, ...)   # [2l, ..., 1, 0]
frequencies   = torch.arange(l, -l-1, -1, ...)
M[..., inds, reversed_inds] = sin(frequencies * angle)
M[..., inds, inds]          = cos(frequencies * angle)

Fix: these three index tensors only depend on l and the device — cache them in a dict keyed by (l, device, dtype). Mathematically identical, eliminates 18 redundant torch.arange dispatches per forward.

2. PYTHON expand_index_int32 — +0.03× speedup

Target: the expand_index buffers used by SO3Linear and the equivariant norms — int64 index tensors fed to torch.index_select.

Fix: cast them to int32 once at startup. Bit-exact (the values are small irrep indices) and halves the bytes that index_select reads. Picks up an additional ~30 ms.

3. NKI wigner_nki_kernel — +0.15× speedup

Target: the entire wigner_D(l, α, β, γ) = Xα · J · Xβ · J · Xγ chain.

What's inefficient: the original PyTorch implementation dispatches ~12 ops per call (3× arange, 2× sin/cos, advanced index_put_, multiple matmuls). Each op pays Neuron dispatcher overhead. With ~2,300 angle values per forward, this is the dominant cost.

How the kernel works: the X matrices have a structured form — non-zero only on the diagonal and antidiagonal. Right-multiplying by a structured X is therefore equivalent to:

(M · X)[b, i, j] = M[b, i, j] · cos(freq[j]·θ) + M[b, i, F-1-j] · sin(freq[j]·θ)

i.e. a fused elementwise op against a "j-reversed" copy of M. The kernel fuses the whole chain:

1. M0      = Xα · J            # elementwise (cos·J_diag + sin·J_anti)
2. M0_jrev = j-reversed M0       # precomputed J_perm constants
3. M1      = M0 · Xβ           # elementwise blend with cos/sin of β
4. M2      = M1 · J             # dense [K,K] structured multiply, unrolled in K
5. out     = M2 · Xγ           # elementwise blend with cos/sin of γ

The full chain becomes one fused HBM-to-HBM call with ~2 nc_matmuls + a handful of elementwise multiplies — no dispatcher trips between stages. Tile size P_MAX=128; B is padded up to a multiple of 128.

Why the chain is mostly elementwise (math)

Xθ is a (2l+1)×(2l+1) rotation about the z-axis in the spherical-harmonic basis. It's diagonal in cos(freq·θ) plus antidiagonal in sin(freq·θ). Multiplying any matrix M by Xθ on the right means: each column of M is independently rescaled by cos(freq[j]·θ) plus the column with reversed index, scaled by sin(freq[j]·θ). That's two same-shape elementwise multiplies and one add — no actual matrix multiplication needed. Only the central J (a fixed permutation-like matrix loaded from Jd.pt) is dense, and that's where the single nc_matmul goes.

4. NKI edge_rot_mat_nki — eliminates 3 CPU fallbacks

Target: init_edge_rot_mat(edge_distance_vec) — builds a 3×3 orthonormal frame per edge for equivariance.

What's inefficient: the original code uses torch.cross and torch.rand_like, both of which fall back to CPU on Neuron, forcing host round-trips for all 460 edges every forward.

How the kernel works:

1. norm_x  = edge_vec / |edge_vec|            # unit edge direction

2. e2 = [0, 1, 0]  if  |norm_x[1]| ≤ 0.9      # deterministic tiebreaker
   e2 = [0, 0, 1]  otherwise                  # replaces torch.rand_like

3. norm_z = (norm_x × e2) / |·|               # expanded to mul/sub form
4. norm_y = (norm_x × norm_z) / |·|

5. rot_mat = stack [norm_z, norm_x, -norm_y]

The deterministic tiebreaker is the key correctness move: the only requirement on e2 is that it not be parallel to norm_x. Two perpendicular candidates ([0,1,0] and [0,0,1]) cover all cases — norm_x can't be parallel to both. The output frame differs from the random baseline by a rotation in the perpendicular plane, but the model is rotation-equivariant in that plane, so energy and forces are unchanged.

The kernel uses a single tile with P_MAX=128 partitions × 3 columns. All ops are fused elementwise multiplies, adds, and a single nl.rsqrt for normalization.

Why this step doesn't always win on wall-clock

The fallbacks in init_edge_rot_mat total ~10–80 ms of CPU time depending on the run, but Neuron's async dispatch can hide a lot of that behind device work. The structural win is real — 0 CPU round-trips for this routine vs. 3 before — but the wall-clock gain is variable (sometimes a wash, sometimes 30 ms). It also unlocks the next patch: with this kernel in place, only one linalg_cross fallback remains in the model.

5. PYTHON torch_cross_explicit — eliminates the last cross fallback

Target: the torch.cross calls in radius_graph_pbc that compute the unit cell volume (a₂×a₃, a₃×a₁, a₁×a₂).

Fix: monkey-patch torch.cross globally with the explicit-indexing form:

def cross(a, b, dim=-1):
    a0, a1, a2 = take(a, 0), take(a, 1), take(a, 2)
    b0, b1, b2 = take(b, 0), take(b, 1), take(b, 2)
    return cat([
        a1*b2 - a2*b1,
        a2*b0 - a0*b2,
        a0*b1 - a1*b0,
    ], dim=dim)

Mathematically identical, but mul, sub, cat are all on-device on Neuron — no fallback. Brings total fallbacks from 8 to 6.

Takeaways

What worked

  • Fusing many small dispatched ops into one NKI kernel (the wigner chain). The dispatcher is the bottleneck, not raw FLOPs.
  • Targeted Python-side fixes (caching, dtype) catch dispatcher overhead without writing a kernel.
  • Replacing fallback ops with mathematically equivalent on-device sequences (torch.cross → explicit indexing).

What's next

  • Atan2/acos kernel for the Euler-angle extraction (so3.py:382–389) — same per-edge hot path as init_edge_rot_mat.
  • End-to-end tracing once the dynamic-shape ops (masked_select, repeat_interleave) are addressed.
  • Static-shape recipe: move radius_graph_pbc outside the traced region, feed pre-built edge_index.
Bottom line. A 1.32× speedup with strict numerical equivalence, achieved via two NKI kernels and three small Python-side patches. The gain comes mostly from eliminating per-op dispatcher overhead rather than improving compute density — which is the right pattern to push further: each remaining fallback is another small kernel away.
