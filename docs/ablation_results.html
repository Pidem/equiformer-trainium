What the model takes as input

Equiformer is a graph neural network for atomic systems. The input is a single batched "data" object containing the atoms and the bonds within a cutoff radius.

FieldShapeDescription
atomic_numbers[N=24]Z for each atom (Na=11, Cl=17)
pos[N=24, 3]3D Cartesian position of each atom (Å)
cell[1, 3, 3]The unit-cell lattice vectors (for periodic boundary conditions)
natoms[batch=1]How many atoms are in each system in the batch
edge_index[2, E=460]For each edge: [source_atom, target_atom]. Built on-the-fly from a 6 Å radius cutoff
cell_offsets[E=460, 3]For PBC: which periodic image of the target atom this edge points to
batch[N=24]Which system in the batch each atom belongs to (all zero here — single system)

Output of the forward pass:

{
  "energy":  [batch=1]    # total energy of the system (eV)
  "forces":  [N=24, 3]    # force on each atom (eV/Å)
}

Why stages ① and ② dominate optimization work

Stage ④ is where the FLOPs are — but it's essentially a pile of linear + softmax + layer_norm, all of which lower well to Neuron's matmul and activation engines. Stages ① and ② are different: they're geometry, not deep learning. They run small ops on small tensors ([1,3,3] cell vectors; [E,3] edge vectors; [E,3,3] rotation matrices), and many of those ops (cross, atan2, acos, rand_like) aren't yet implemented in the Neuron backend.

Per fallback, the cost isn't the math — it's the host round-trip. With ~6 fallback ops × ~60 invocations across the 460-edge graph, the dispatcher overhead becomes dominant. This is exactly where the ablation patches focus.

Where each patch sits in the forward pass

What each patch does

1. PYTHON wigner_cache — +0.11× speedup

Target: wigner._z_rot_mat(angle, l), called 6× per forward (3 angles × 2 layers).

What it patches: The function builds a sparse rotation matrix where cosines lie on the diagonal and sines on the antidiagonal. Each call rebuilt the index tensors from scratch:

inds          = torch.arange(0, 2*l+1, ...)      # [0, 1, 2, ..., 2l]
reversed_inds = torch.arange(2*l, -1, -1, ...)   # [2l, ..., 1, 0]
frequencies   = torch.arange(l, -l-1, -1, ...)
M[..., inds, reversed_inds] = sin(frequencies * angle)
M[..., inds, inds]          = cos(frequencies * angle)

Fix: these three index tensors only depend on l and the device — cache them in a dict keyed by (l, device, dtype). Mathematically identical, eliminates 18 redundant torch.arange dispatches per forward.

2. PYTHON expand_index_int32 — +0.03× speedup

Target: the expand_index buffers used by SO3Linear and the equivariant norms — int64 index tensors fed to torch.index_select.

Fix: cast them to int32 once at startup. Bit-exact (the values are small irrep indices) and halves the bytes that index_select reads. Picks up an additional ~30 ms.

3. NKI wigner_nki_kernel — +0.15× speedup

Target: the entire wigner_D(l, α, β, γ) = Xα · J · Xβ · J · Xγ chain.

What's inefficient: the original PyTorch implementation dispatches ~12 ops per call (3× arange, 2× sin/cos, advanced index_put_, multiple matmuls). Each op pays Neuron dispatcher overhead. With ~2,300 angle values per forward, this is the dominant cost.

How the kernel works: the X matrices have a structured form — non-zero only on the diagonal and antidiagonal. Right-multiplying by a structured X is therefore equivalent to:

(M · X)[b, i, j] = M[b, i, j] · cos(freq[j]·θ) + M[b, i, F-1-j] · sin(freq[j]·θ)

i.e. a fused elementwise op against a "j-reversed" copy of M. The kernel fuses the whole chain:

1. M0      = Xα · J            # elementwise (cos·J_diag + sin·J_anti)
2. M0_jrev = j-reversed M0       # precomputed J_perm constants
3. M1      = M0 · Xβ           # elementwise blend with cos/sin of β
4. M2      = M1 · J             # dense [K,K] structured multiply, unrolled in K
5. out     = M2 · Xγ           # elementwise blend with cos/sin of γ

The full chain becomes one fused HBM-to-HBM call with ~2 nc_matmuls + a handful of elementwise multiplies — no dispatcher trips between stages. Tile size P_MAX=128; B is padded up to a multiple of 128.

Why the chain is mostly elementwise (math)

Xθ is a (2l+1)×(2l+1) rotation about the z-axis in the spherical-harmonic basis. It's diagonal in cos(freq·θ) plus antidiagonal in sin(freq·θ). Multiplying any matrix M by Xθ on the right means: each column of M is independently rescaled by cos(freq[j]·θ) plus the column with reversed index, scaled by sin(freq[j]·θ). That's two same-shape elementwise multiplies and one add — no actual matrix multiplication needed. Only the central J (a fixed permutation-like matrix loaded from Jd.pt) is dense, and that's where the single nc_matmul goes.

4. NKI edge_rot_mat_nki — eliminates 3 CPU fallbacks

Target: init_edge_rot_mat(edge_distance_vec) — builds a 3×3 orthonormal frame per edge for equivariance.

What's inefficient: the original code uses torch.cross and torch.rand_like, both of which fall back to CPU on Neuron, forcing host round-trips for all 460 edges every forward.

How the kernel works:

1. norm_x  = edge_vec / |edge_vec|            # unit edge direction

2. e2 = [0, 1, 0]  if  |norm_x[1]| ≤ 0.9      # deterministic tiebreaker
   e2 = [0, 0, 1]  otherwise                  # replaces torch.rand_like

3. norm_z = (norm_x × e2) / |·|               # expanded to mul/sub form
4. norm_y = (norm_x × norm_z) / |·|

5. rot_mat = stack [norm_z, norm_x, -norm_y]

The deterministic tiebreaker is the key correctness move: the only requirement on e2 is that it not be parallel to norm_x. Two perpendicular candidates ([0,1,0] and [0,0,1]) cover all cases — norm_x can't be parallel to both. The output frame differs from the random baseline by a rotation in the perpendicular plane, but the model is rotation-equivariant in that plane, so energy and forces are unchanged.

The kernel uses a single tile with P_MAX=128 partitions × 3 columns. All ops are fused elementwise multiplies, adds, and a single nl.rsqrt for normalization.

Why this step doesn't always win on wall-clock

The fallbacks in init_edge_rot_mat total ~10–80 ms of CPU time depending on the run, but Neuron's async dispatch can hide a lot of that behind device work. The structural win is real — 0 CPU round-trips for this routine vs. 3 before — but the wall-clock gain is variable (sometimes a wash, sometimes 30 ms). It also unlocks the next patch: with this kernel in place, only one linalg_cross fallback remains in the model.

5. PYTHON torch_cross_explicit — eliminates the last cross fallback

Target: the torch.cross calls in radius_graph_pbc that compute the unit cell volume (a₂×a₃, a₃×a₁, a₁×a₂).

Fix: monkey-patch torch.cross globally with the explicit-indexing form:

def cross(a, b, dim=-1):
    a0, a1, a2 = take(a, 0), take(a, 1), take(a, 2)
    b0, b1, b2 = take(b, 0), take(b, 1), take(b, 2)
    return cat([
        a1*b2 - a2*b1,
        a2*b0 - a0*b2,
        a0*b1 - a1*b0,
    ], dim=dim)

Mathematically identical, but mul, sub, cat are all on-device on Neuron — no fallback. Brings total fallbacks from 8 to 6.

Takeaways

What worked

  • Fusing many small dispatched ops into one NKI kernel (the wigner chain). The dispatcher is the bottleneck, not raw FLOPs.
  • Targeted Python-side fixes (caching, dtype) catch dispatcher overhead without writing a kernel.
  • Replacing fallback ops with mathematically equivalent on-device sequences (torch.cross → explicit indexing).

What's next

  • Atan2/acos kernel for the Euler-angle extraction (so3.py:382–389) — same per-edge hot path as init_edge_rot_mat.
  • End-to-end tracing once the dynamic-shape ops (masked_select, repeat_interleave) are addressed.
  • Static-shape recipe: move radius_graph_pbc outside the traced region, feed pre-built edge_index.
Bottom line. A 1.32× speedup with strict numerical equivalence, achieved via two NKI kernels and three small Python-side patches. The gain comes mostly from eliminating per-op dispatcher overhead rather than improving compute density — which is the right pattern to push further: each remaining fallback is another small kernel away.
